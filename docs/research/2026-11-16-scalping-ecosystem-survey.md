# 中国演出票代抢生态与开源实现调研

**调研日期：**2026-11-16  
**范围：**中国大陆，重点关注闲鱼、淘宝上的代抢/软件销售，以及大麦、猫眼演出票。  
**用途：**为反制脚本抢票提供威胁画像与产品、风控和取证线索。

## 一、核心结论

1. **“代抢”不是单一技术。**公开材料至少显示人工代拍、浏览器自动化、安卓界面自动化、余票监控、批量账号/设备，以及直接构造购票请求等路径。各路径的速度、规模和违法风险差别很大，不能把所有代抢都等同于绕过平台安全防护。[S1][S2][S3][G1][G2]
2. **闲鱼、淘宝更像获客与交付渠道，而非技术本体。**公开报道记录了“人工代抢”“抢票秘笈”“抢票软件”“保中/不成退款”等商品或话术；警方披露过通过闲鱼销售面向大麦、猫眼等平台脚本的案件。实际履约可由卖家人工、脚本作者、设备群或外部“票务”团队完成。[S1][S4][S5] 不能由商品文案推断真实出票能力。
3. **强实名改变了交易结构。**代抢往往先收集观演人的姓名、证件信息或账号权限，再在开售时下单；这形成个人信息泄露与冒充官方“录入”诈骗风险。警方、检察机关的案例证明自动化与诈骗两类风险会混杂，但应分别识别。[S2][S6][S7]
4. **最值得优先防的，是规模化和绕过安全验证的行为。**检察机关披露的案件包括手机墙、批量账号、设备与 IP 切换，以及绕过人机验证、构造请求直接下单。开源仓库更多展示界面自动化，不能据此推断它们具备上述绕过能力。[S2][S3]
5. **“秒没”不能单独证明脚本抢票。**公开票量、预留票、需求远超供给、渠道分配及异常流量都可能影响体感；应结合售票日志、库存流向与实际实名入场数据分析。[P1][S8]

## 二、交易与技术链条

| 环节 | 公开可见做法 | 反制时应看什么 | 证据等级 |
|---|---|---|---|
| 招揽客户 | 闲鱼/淘宝上发布代抢、软件或教程商品；宣称“专业”“保中”“失败退款” | 商品页面、店铺、聊天、服务费/退款条款、导流账号 | 媒体调查与警方个案 [S1][S4][S5] |
| 收集订单 | 提前取得演出、场次、票档、观演人信息；有卖家要求登录买家账号 | 信息收集字段、账号授权方式、是否索取验证码/密码 | 媒体调查与检察案例 [S2][S6] |
| 执行抢票 | 人工分工、Selenium/CDP 浏览器控制、Appium/AutoX.js/ADB 安卓控制、轮询余票与定时触发 | 同步操作节奏、重复路径、跨账号设备关联、失败重试模式 | 仓库自述；仅证明代码/功能声称存在 [G1]–[G5] |
| 高风险升级 | 大量设备/账号并行；绕过验证、获取凭据/数据、构造请求下单 | 人机验证结果与订单不匹配、异常会话/凭据使用、集中账户簇 | 检察机关披露的涉案鉴定/供述 [S2][S3] |
| 交付和售后 | 成功收服务费、失败退款；少数以“内部名额/票夹录入”诱导脱离平台支付 | 付款去向、是否进入官方订单、是否引导屏幕共享 | 媒体与反诈报道 [S4][S7] |

**关键区别：**浏览器/手机界面自动化通常仍沿正常页面走流程；直接构造请求、绕过验证或获取未授权数据属于不同威胁层级。江苏检察网所述案件曾通过功能鉴定区分普通辅助工具与涉嫌侵入系统的软件。[S2]

## 三、闲鱼/淘宝代抢市场观察

- **商品形态。**2023 年《北京青年报》调查记录人工代拍、按次收费的程序代拍以及单独出售软件；其中“90% 成功率”是卖家说法，并非独立测试结果。[S6] 2025 年峡江县公安局通报一宗闲鱼售脚本案：普通脚本标价 8.8–9.9 元、定制 400–1000 元，面向大麦、猫眼、纷玩岛；这些是**该案历史价格**，不能外推到当前市场。[S1]
- **分工。**检察日报披露的镇江案件中，网店运营者负责获客与销售，程序员负责研发和抢票，另租服务器承接订单；说明平台店铺未必是技术实施者。[S2]
- **人工仍存在。**媒体调查曾在闲鱼、淘宝看到“专业人工代抢”商家，也报道部分卖家转向人工和招募抢手。不能仅凭“人工”文案排除后台自动化，也不能反推它必然存在。[S4]
- **诈骗混入。**“内部渠道”“票夹录入”“系统异常”等说辞可能把用户引至伪造支付页或屏幕共享。《澎湃新闻》记录了一起从闲鱼引流的冒充大麦内部人员骗局；该类案件应从真实脚本代抢中单列。[S7]
- **本次观察边界。**未登录或抓取闲鱼、淘宝实时商品页；没有做当前在售数量、成交量、成功率或价格分布统计。以上结论来自可核查的警方、检察机关、媒体历史材料。

## 四、GitHub 开源实现样本

以下为**公开仓库的静态阅读**，没有运行脚本、接入账号或验证抢票成功率。README 的功能和性能数据均视为作者自述；仓库存在不代表目前可用、合规或被实际黄牛采用。

| 仓库 | 目标与方式 | 与反制相关的观察 | 核验结论 |
|---|---|---|---|
| [Pactum7/ticket-grabbing][G1] | 猫眼、纷玩岛；基于 AutoX.js 的安卓界面自动化。大麦仅列为计划中的余票通知 | 猫眼有卡点进入和余票监控两种脚本，后者声称自动选择观演人、刷新和通知 | 猫眼实现可见；**不能称其已支持大麦抢票** |
| [yanzilee/damaiTickets][G2] | 大麦；Web Selenium、Mobile Appium、Desktop 三路 | 作者当前推荐 Mobile；Web 保留，Desktop 的 H5/接口路线自述受风控限制、稳定性不足 | 多路线技术对照；不可把过时路线算作有效能力 |
| [TsungShr/ticket-sniper][G3] | 猫眼/大麦使用安卓 ADB；票星球使用 HTTP API | 展示跨平台协调、校时与设备操作；**其 HTTP 直连对象是票星球，不是猫眼或大麦** | 可用于识别多平台并行模式；性能数字未经独立验证 |
| [chl-5g/damai-ticket][G4] | 大麦；连接已登录浏览器的 CDP 辅助脚本 | 自动导航、预选场次/票档、轮询按钮、提交订单；支付由人工完成 | 说明浏览器会话复用型自动化 |
| [LiLeo505/ticket-puchase][G5] | 大麦；Appium + UiAutomator2 安卓 App 自动化 | 自动选择票价、数量、观演人并提交订单；README 说明 Web 版已移除 | 说明移动端控件自动化 |

**不要混淆实现方式。**上述样本既包括个人辅助脚本，也包括面向多个平台的工具；没有证据证明这些仓库与闲鱼/淘宝具体卖家、检察机关案件或真实交易存在联系。

## 五、反制优先级与可验证指标

### 1. 平台售票侧

| 优先级 | 建议 | 验证指标与注意点 |
|---|---|---|
| 高 | 以“账号—设备—网络—观演人—支付”关联图识别批量簇，并对开售前后的集中行为进行分层处置 | 同设备多账号、同账号多设备、跨账号共用观演人/支付标识、重复失败重试。共享网络或家庭设备会误伤，需多信号结合。 |
| 高 | 在库存查询、锁票、订单提交三个节点校验会话与前序页面流程的一致性；记录验证结果 | 关注缺少正常流程却能下单的会话、验证未通过后仍产生订单、异常高的锁票/付款落差。避免公布可反推阈值的规则。 |
| 高 | 限制单账号/设备短时高频锁票与重试，采用排队或动态节流；保留公平性与申诉机制 | 比较异常请求占比、正常用户完成率、误封申诉率、售罄时延；不要仅以速度判恶意。 |
| 中 | 加强实名购票、实名入场和退票回流链路的核验；让真实用户能合理退票 | 核对单证件单场次一票、入场一致性、退票释放去向。适用大型演出规则见 [P1]。 |
| 中 | 对公开票量、渠道配额与非公开票流向建立审计台账 | 用核准容量、公开销售量、预留票、锁票、支付、退票和入场数据解释“秒没”；避免把供给问题全归于机器人。[P1][S8] |

### 2. 电商与消费者侧

- 对“保中”“内部名额”“官方录入”“技术绕过”“代抢软件”等商品与聊天话术做**人工复核后**的分级处置；保留页面、订单、聊天和收款证据，避免关键词一刀切影响合法咨询与普通转让。[S1][S7]
- 官方售票渠道和授权代理名单应在演出页面清晰公示；对伪造的官方支付页、二维码和客服账号建立快速举报链路。[P1][S7]
- 面向购票者提示：不要向代抢卖家交出账号密码、短信验证码、完整证件资料；不要因“出票异常”开启屏幕共享。是否存在合法人工服务应依具体交易判断，不能把所有代拍一概定性。[S6][S7]

## 六、建议的下一轮实证工作

1. **建立合规样本库。**记录公开商品的时间、平台、关键词、价格、承诺、销量显示、导流方式、要求的信息字段；只采集公开信息并去标识化，不购买软件或提交真实身份资料。
2. **与票务平台协作做售票事件复盘。**选取 1–2 场异常显著的演出，把库存分配、登录、验证、锁票、支付、退票、实名入场日志按时间线对齐，计算自动化嫌疑簇的实际购票份额。
3. **以正常用户体验作对照。**每项风控同时报告误伤率、正常用户下单成功率和申诉处理时间；避免把公平购票问题转化为普遍的人机验证负担。
4. **分开追踪四类问题。**界面自动化、绕过安全防护、票源/渠道不透明、代抢诈骗各有不同证据和治理主体。

## 六点五、接口逆向路线评估（2026-11-16 补充，第六轮）

用户问到的 [cnblogs 文章](https://www.cnblogs.com/damaidamai/articles/18103810) 是一篇 **Frida + mtop 接口逆向**教程（2023，App 8.5.4，Bluestacks root 模拟器）：frida-trace 跟踪 MtopBusiness/InnerSignImpl，hook 出 mtop 签名调用链，再用 frida RPC 让 Python 直接调 APK 内部类下单（单次 0.024s）。同路线文章还有：CSDN《大麦抢票协议逆向实战指南》（直接生成 sign 算法）、MakiNaruto/Automatic_ticket_purchase（5798★，Selenium Web 端 + signcode.js 逆向签名，2024-03 停更）。

**评估：技术路线本身不采用**——hook/逆向签名/注入属于我们的合规红线（与"不做接口签名逆向"一致），且风险面完全不同：Frida 注入是 App 明确检测项（su/Magisk、Xposed、Frida、模拟器特征、Bootloader 解锁），一旦命中是**静默限流降权而非封号**，账号会在不知情中被废掉战力。

**但可吸收的情报**（来自 CSDN《大麦网抢票工具实战：接口分析与风控避坑指南》2026-10 及相关文章，该文同样立场合规："签名参数原样携带不破解、滑块人工处理、支付手动完成"）：

1. **下单重试纪律**：超时重试最多 3 次即放弃（大概率已到限流阈值）；明确返回"库存不足"时不再重试（高频重试反而触发风控）——纳入热路径设计；
2. **支付边界**：抢票只负责到"生成订单号"，订单=锁库存，30 分钟支付窗口内人工完成支付；自动支付风险高一个层级，不做（与既有红线一致）；
3. **`extend` 字段 = 观演人信息 JSON**，强实名下单必需——DM-05 提交参数设计参考；
4. **多账号风控聚类**：同出口 IP 高频聚合流量 + 相同 UA/指纹会被聚类标记整组风险账号——印证 P1"一账号一设备（指纹）"设计的必要性；
5. **回流票释放规律**（7×24 轮询实测，P4 余票监控的时间窗参考）：开票后 5–15 分钟（未支付订单过期）★★★★★、演出前 3–7 天（退票）★★★★、每日 10:00–14:00 ★★★、演出前 24h ★★★；
6. **风控软化认知**："不是检测到就封号，而是静默限流"——解释了"访问被拒绝"类软拦截，也提示账号健康度需要长期观察，不能只用一次就下结论；
7. **市场情报**：付费代抢软件 99% 是坑（套壳拉黑、用 2 天封号），自研 + 人工兜底才是可持续路线——与 P0 自购自验证定位一致。
