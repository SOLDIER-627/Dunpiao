## 与参考仓库对照后的取舍

1. [HaTickets Mobile](https://github.com/currycan/HaTickets/tree/master/mobile) 的 `rush_mode`、坐标缓存、单 ID 快查询与快速轮询已部分吸收到当前脚本：`wait_timeout=0`、50ms 快查询、CTA/SKU 坐标锚点、状态转换后才做 XML dump。继续照搬其“跳过读取”的速度参数，可能失去大麦 9.0.38.6 图片化票档与订单字段的核验证据。[HaTickets 购票逻辑](https://github.com/currycan/HaTickets/blob/master/docs/mobile-ticket-logic.md)包含场次/价格选择分支，需以本机页面验证。
2. [WECENG 的 Appium V2](https://github.com/WECENG/ticket-purchase/blob/master/damai_appium/app.md)用显式等待和短点击减少通用等待；当前 u2 方案已改为按状态轮询、`input tap` 约 0.1s。其 Appium `clickGesture` 不能直接视为本机 HyperOS 的提速替代，且本机票档文本比其样本更难读取。
3. 早期仓库的 `price_index`/预选能缩短选择路径，但只适合**目标场次、票档映射已预校准且当前布局被复核**的场景。现在“5 档中 4 档缺货、唯一候选 ¥780”是单场样本，不能泛化为任何新演出；新演出需要[预检方案](../architecture/大麦真机端到端脚本方案_2026-11-18.md)的场次、票档逐屏采集。

## 已落地与待做

**已落地：**`scripts/e2e_run.py` 增加订单字段就绪判断。无提交演练若 `s2_after` 首帧已有提交按钮、张数与金额，就直接复用该 XML，省去一次紧随其后的完整 dump；正式 `--submit` 仍使用第二次快照核对，避免为提速缩短订单页观察。现有 11:10 的 `s2_after.xml` 离线判定字段已齐。新增 SKU 标签变化时间线日志（每次变化的相对毫秒数与计数），供下一轮验证“晚渲染”分布。两个改动都未触发新订单。

**优先做的实验：**连续多次**无提交**运行，统计“SKU 进入 → 首个缺货标签 → 最后一次标签变化 → XML 完成”的分布，并在单档、多档、全售罄、库存变化时分别采样。若有稳定、可识别的“票档面板加载完成”信号，可用它替代固定 0.8s 窗口；仅凭一场的标签数量或预缓存坐标直接抢点，证据不足。要证明收益，须同时验证没有误选缺货档或错误票价。

**下一项较小优化：**研究订单页针对张数、金额、观演人的快速定向复核，保留一次完整 XML 为正式提交证据。当前金额/张数节点没有稳定资源 ID，不能直接替换第二次 dump；如果后续能建立可靠、跨样本的定位方式，再比较耗时与漏检风险。

**先补正确性：**当前 `e2e_run.py` 的默认金额和演出标签仍针对本次样本，订单核对主要覆盖张数、金额、观演人；标题、场次、票档仍需接入新演出配置与订单页核对。实现通用场次/票档选择之前，不应以这条单场次热路径的速度作为正式多场次能力。
