# dunpiao 原理与流程

本文说明两模式（抢票 / 回流）共用的执行引擎、关键设计纪律与耗时模型。
使用说明：[抢票模式](抢票模式.md) · [回流模式](回流模式.md) · [AI 助手配置](AI助手配置.md) · [README](../README.md)

方法基线：上游 [HaTickets](https://github.com/) Mobile（固定 commit `76946bf`）的真机 uiautomator2 代码，按本机实测改造。**参考上游、不自造**是本项目的基本纪律。

## 1. 一句话定位

在用户自己的大麦账号上，把「详情页待命 → 下单 → 停在付款前」压缩到秒级，**付款永远人工**；不做验证码代解、签名逆向、接口直调、自动支付。

## 2. 顶层流程

两条路径，触发后共用同一套执行链：

```
抢票模式（rush.py）
┌─ 开售前（人工）───────────────────────────────┐
│ 大麦 App 内完成 预约 + 预选（目标场次+票档）    │
│ --capture-coords 预填坐标缓存（只信 CTA）      │
└──────────────────────────────────────────────┘
  clock_sync 采样 → 信任分级 → 单调 deadline
    → 剩余 ≤ lead(3s)：prewarm 快照（只侦察不点击）
    → T0 直点 CTA
                  │
回流模式（reflow.py）  │
┌─ 进 SKU 面板 ────┐  │
│ 两级面板：点场次  │  │
│ 目标票档缺货登记？│  │
│  在 → 周期刷新蹲  │  │
│  消失 → 触发 ────┼──┤
└─────────────────┘  │
                     ▼
      共用执行链（engine.py）
   ① 点票价（预选生效则跳过）
   ② 点确定  → 确认页出现判定（自愈链：重测/文本匹配/元素回退）
   ③ 订单页全字段核对（金额/张数/场次日期/观演人/实勾数）
   ④ 提交前四类阻塞弹窗筛查（consent/待支付/验证码/瞬时错误）
   ⑤ 点立即提交（单次，不盲重试）
   ⑥ 提交后只读验证（五分类，不再发出任何点击）
   ⑦ 收银台 → 终止 → 人工付款
```

## 3. 各阶段原理

### 3.1 开售等待：clock_sync + prewarm

- **时钟**：Mac SNTP + 设备双采样测偏移，开售时刻映射到**单调时钟**（不受系统改时间影响）；信任分级 severe（未同步/偏移过大）默认拒绝继续。
- **prewarm（T0 前 ~3s）**：一次带像素的快照做三件事——CTA 容器可见（不可见直接停，不盲等）、像素亮橙判定（购买态）、文案护栏（「预约/预售」类文案拦截直点）。**只侦察，不点击**。
- **T0 直点的资格**：prewarm 三项通过 + T0 前 activity 仍是详情页。否则降级为「验证路径」（缓存坐标→文案护栏→入口轮询兜底）。

### 3.2 T0 三击与「点击不被信任」

脚本从不假设点击成功。每次点击后紧跟状态验证：

- CTA 点击 → 入口轮询（0.45-3s，0.03s 粒度）确认进了 SKU/订单页；没进→双击重试→dump 路径
- 确定点击 → 确认页出现判定；没出现→自愈链（见 3.3）
- 提交点击 → 只读验证（见 3.6）

**HyperOS 实测**：uiautomator2 无障碍点击经常被吞，所以点击层统一用 `shell input tap`，元素点击只作回退且必须验状态。

### 3.3 坐标缓存与自愈链

- 缓存（`logs/coords_cache.json`）按 show_tag 存 CTA/票价/确定按钮坐标，只存坐标不存决策。
- **预约态坐标低信任**：预约面板票卡只有「可预约」文本、无价格无选中态，且坐标是视口相对的（面板滚动会变）——所以缓存只信 CTA，票价/确定以开售后重测为准。
- **自愈链**：连点未确认 → 重测 dump → `¥价格` 文本匹配目标档（对滚动免疫）→ 再连点 → 元素点击回退 → STOP。链条不可删。
- **安全修正**：批量连点是 `[票价, 确定]` 不含尾部第二次确定——尾部确定会落到订单页「立即提交」同位 bar，构成绕过闸门的提交风险。

### 3.4 订单核对：真正的闸门

提交前核对四项，**任一不过就停机**：

1. 金额 == `--expected-total`
2. 数量 ×1 张
3. 观演人姓名在页面且各出现一次
4. checkbox 实勾数 ≥ 观演人数

订单是否真的已处理只有用户能确认（大麦 App 自身有「已有待支付订单」拦截），所以提交记录 `submit_record.json` 只做审计不拦截。

### 3.5 提交前筛查：四类阻塞弹窗

复用核对阶段的 dump（零额外耗时），按上游 `page_probe.py` 词表做**纯文本分类**——不定位弹窗、永不点弹窗本身：

| 类 | 识别 | 处置 |
|---|---|---|
| consent 授权弹窗 | 资源 ID `id_boot_action_agree` | 停机不提交 |
| pending_order 待支付弹窗 | 「未支付/待支付订单」文案 | 停机不提交（无法归属本次运行） |
| manual_verification 验证 | 滑块/人机验证/安全验证… | 停机（红线，交人工） |
| transient_error 瞬时错误 | 网络/加载类文案 + **本地配对**重试控件 | 恢复（点重试）→ 复验字段 → 才提交 |

配对证明（上游 `_is_local_transient_retry_pair`）：重试控件必须与错误标记在最近公共祖先 ≤1 条边内相会、且共同容器具备错误容器语义；配对不出**就不点**（fail-closed）。

### 3.6 提交后只读验证：五分类

上游核心纪律：**提交一次，之后验证只读，不再发出任何点击**——防重复下单。五分类判定：

1. 支付页 activity/文本信号 → 成功，待用户支付
2. 售罄（已售罄/库存不足/暂时无票）→ 停机
3. 验证码/人机验证 → 停机（红线）
4. 「未支付」文本 → 无法归属本次提交，停机交人工核实
5. 其余一切 → **结果未知**，审计记 `result_unknown`，提示人工在大麦订单列表核实

「抢票人数太多，请继续尝试」这类居中弹窗即属第 5 类：脚本不代点，人工点「继续尝试」。

### 3.7 为什么弹窗不自动处理：scrim 认知

居中 modal 弹窗带全屏 scrim，**吃掉屏幕上任何位置的脚本点击**。所以上游的模型是：点击前分类（认识的才有对策）、点击后状态验证兜底（点击被吃=页面没转换=重试链→超时停机）。弹窗存在期间脚本等于失权，正确动作是安静退场把控制权还给人——这也是不重复下单的保障。

## 4. 关键设计纪律（继承自上游）

1. **提交一次**：selector 回退只在首次成功点击前；之后验证只读 fail-closed
2. **fail-closed**：识别不了/配对不出/时钟不可信/字段不齐——一律停机，绝不猜测着继续
3. **点击不被信任**：一切点击靠点击后的状态验证确认
4. **快路径只做轻量动作**：热路径零 dump（缓存坐标直点），dump 只出现在自愈链和筛查点
5. **参考上游、不自造**：遇分歧先读上游代码

## 5. 耗时模型（真机实测，Xiaomi 14 / HyperOS）

| 分段 | 实测 |
|---|---|
| T0 直点 CTA 偏差 | ~1-45ms |
| CTA → 面板打开 | 0.15-0.30s |
| 驻留 + 首批连点 | 0.4s + 0.9s 窗口 |
| 预选生效：T0 → 订单确认页 | **~1.0s**（实战含一次预选未命中为 2.5s） |
| 提交 → 收银台 | 2.78s（大麦建单地板，不可优化） |
