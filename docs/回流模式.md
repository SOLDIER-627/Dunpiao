# 回流模式（缺货登记蹲回流）

入口：`scripts/reflow.py`　｜　原理细节：[原理与流程](原理与流程.md)

## 一句话

盯着目标票档的「缺货登记」标记，**它一消失就立刻走三击执行链**（点票价 → 确定 → 核对 → 提交 → 收银台），付款人工。

## 为什么需要专门的刷新

大麦 SKU 面板的库存**不会自动刷新**——缺货登记的票档会一直挂着「缺货登记」，即使别人退票放出了库存。所以监听循环必须周期性重进面板：

```
BACK（回详情页）→ CTA（重开面板）→ 点选场次 → dump 看目标票档缺货登记是否消失
```

一轮开销约 2-5s，所以 **`--reflow-refresh` 就是发现延迟**（默认 60s，实测建议 15s）。

## 两级面板（重要）

部分演出的 SKU 面板是**两级**结构（实测 2026-11-18 F✦FOREVER 上海场）：

```
第一级：场次列表（场次项自绘，无障碍树无任何文本）
第二级：票档列表（点选场次后才加载）
```

三条必须知道的实测结论：

1. 面板刚打开**只显示场次列表**，没有票档
2. **BACK 重进面板不记得场次** → 每次刷新都要重选场次（`reflow.prepare_tiers` 已实现）
3. 场次项**日期文本读不到**（自绘）→ 只能按序号 `--session-index` 点选；
   最终防线是 `--expect-session-date`（订单页场次文本核对，订单页确实有 `2026.11.21 18:30` 这样的文本）

若某演出的场次卡带日期文本（`cn.damai:id/sku_panel_dates` + `tv_date`），脚本会**优先按日期匹配**（移植上游 `event_navigator.select_session`：日期+城市唯一 → 日期唯一 → 序号回退）。

## 命令

```bash
# 蹲守（不提交，触发后只到订单页核对）
.venv/bin/python scripts/reflow.py --show-tag <tag> --expected-total 488.00 \
    --session-index 1 --expect-session-date 2026.11.21

# 蹲守 + 单次授权提交（触发即走完到收银台）
.venv/bin/python scripts/reflow.py --submit --show-tag <tag> --expected-total 488.00 \
    --session-index 1 --expect-session-date 2026.11.21 \
    --reflow-interval 2 --reflow-refresh 15 --reflow-max-minutes 300

# 后台跑（日志落盘）
nohup .venv/bin/python -u scripts/reflow.py --submit ... > logs/reflow_<tag>.log 2>&1 &
# 停：kill <pid>
```

## 参数

| 参数 | 默认 | 作用 |
|---|---|---|
| `--session-index` | — | 场次序号（0-based，面板从上到下）；两级面板必填 |
| `--expect-session-date` | — | 订单页场次护栏（如 `2026.11.21`），不符则 STOP 不提交 |
| `--reflow-interval` | 2.0 | 监听 tick 间隔（每 tick 一次 dump） |
| `--reflow-refresh` | 60 | 周期重进面板刷新库存的间隔（≈发现延迟） |
| `--reflow-max-minutes` | 120 | 监听总时长上限 |
| `--reflow-require-text` | — | 护栏文本（可多次）：dump 可见文本必须全含，否则视为落错场次并重进 |
| `--submit` | 关 | 触发后自动提交（核对全过才点） |

回流模式**自动关闭预选**：面板底部是 `¥0`（未选档），必须显式点票价再点确定。

## 监听循环做了什么

```
每 tick：
  1. activity 快查：不在 SKU 页 → BACK/CTA 重进
  2. 到 --reflow-refresh → 强制重进（刷新库存）
  3. 票档层就绪检查（两级面板：无票档 → 按 --session-index 点场次，有界等待 2.5s）
  4. dump → 「我知道了 / 知道了 / 下次再说 / Cancel」轻量弹窗点掉（上游词表）
  5. 护栏文本校验（--reflow-require-text）
  6. 目标票档区域是否还有不可购词（缺货登记/已售罄/无票/暂时不可售…上游 price_selector 词表）
       还有 → 继续蹲
       没有 → 可购信号 → 接管执行链（点票价 → 确定 → 订单页核对 → 提交 → 收银台）
```

## 二次回流

提交后如果页面显示已售罄（上游 `sold_out`），回流模式**回到监听继续蹲**，审计记 `sold_out`；验证码 / 待支付归属不了 / 结果未知仍然停机交人工。

## 实测节奏（2026-11-18）

| 环节 | 实测 |
|---|---|
| tick（dump + 判定） | ~0.3s |
| 一次刷新（BACK+CTA+选场次+2 次 dump） | ~4-5s |
| 点场次 → 票档出现 | ~1.2s |
| 触发后 → 订单页 | ~3.1s |
| 触发后 → 收银台 | ~5.3s |

## 常见 STOP

| STOP | 原因 | 处置 |
|---|---|---|
| 场次项不足（需要 index=N，实际 M 项） | 面板未渲染完 / 场次序号超范围 | 用 `show_info.py` 重新提取场次项数量 |
| 面板未渲染（既无票档也无场次项） | 页面卡住或不在 SKU 面板 | 看屏幕；必要时手动回详情页重跑 |
| 票档容器缺失或序号越界 | `price_index` 超出该场次票档数 | 用 `show_info.py` 重新提取票档序号 |
| 回流监听超时 | 到时限没等到回流 | 延长 `--reflow-max-minutes` 或换票档 |
| 核对未全通过 | 金额/场次/观演人不符 | 按 `s3: 订单核对 {...}` 逐项查 |
| 该设备已有另一个运行器在跑 | 单实例锁被占用 | `kill <pid>` 后重跑 |
