## 二、E2E-12：主流程重构（commit `1612864`）

`scripts/e2e_run.py` 核心流程 = 上游四阶段：

| 阶段 | 实现 | 删除的旧机制 |
|---|---|---|
| Phase 1 详情页 | 单 dump → CTA 容器坐标 → 文案护栏（零成本挂同一 dump）→ shell 点击 | CTA 亮橙像素等待 |
| Phase 2 入口等待 | SKU 标记/确认页快查询 0.45s@0.03；超时回退 CTA 双击（上游 `_open_purchase_panel`） | — |
| Phase 3 SKU 页 | 单 dump → 票价（`price_index` 索引，flowlayout 子 FrameLayout+clickable）+ `btn_buy_view` 双坐标；缺票价 0.3s 重 dump | 缺货标签稳定窗口 |
| Phase 4 确认 | shell 批量连点循环 ≤0.9s；确认判定=checkbox/确认购买/实名观演人/立即提交（0.02s 粒度）；回退元素点击 0.55s | 确定按钮像素亮橙轮询 |
| Phase 5 订单页 | 观演人 checkbox 补选（只点未勾选的）→ 全字段核对 →（--submit）单次提交闸门 → 收银台即停 | — |

**保留的本仓库设施**（上游方法之外的审计/合规层）：提交闸门体系（单次授权/submit_record.json/--clear-record/收银台即停）、`--wait-open`（clock_sync+prewarm，E2E-07 成果）、文案护栏、证据落盘、s0 BACK 恢复阶梯、订单全字段核对（新增 `attendees_checked` 实勾数校验）。`--rush` 参数保留为兼容 no-op。

## 三、E2E-13：坐标缓存与二次提速（commit `da4e6fc`）

用户新点：**预约态即可进 SKU 页测量坐标**——开票只改 CTA 容器内文案，不改容器位置；场次/票档不变则 SKU 坐标不变。开票前预填，T0 直接用缓存坐标。

- 新文件 `src/dunpiao/coords_cache.py`：上游 `_cached_coords`/`_put_hot_coord`（进程内存）的**持久化版**，`logs/coords_cache.json`，键=`show_tag`。**只存坐标不存决策**。
- 信任分层（照上游 formal/rush 分层）：复用前廉价校验=屏尺寸/`price_index`/三点屏内/activity 是详情页/入口轮询确认 SKU 页，全程不 dump。
- `--capture-coords` 测量模式：预约态走到 SKU 页写缓存即停（不连点不进单）。
- 失败自愈链：缓存连点未确认 → 重测 dump → **坐标没变也再连点一轮**（此时距入口 ~1.5s，是 dump 路径屡试不爽的时延区）→ 仍失败元素回退 → STOP。实测 4/4 到单。
- checkbox 状态从 s2_after XML 直读，全勾跳过 u2 逐个 `.info`（省 ~0.8s）；首帧字段已齐复用快照核对（省 ~0.5s）。

### 重要安全修正：批量连点 [票价,确定,确定] → [票价,确定]

上游原版三连点的**尾部确定点击**在订单页已打开且触摸就绪时，会正好落在「立即提交」同位 bar 上（`btn_buy_view` 与订单提交按钮同位坐标 (931,2580)），有**绕过提交闸门**的风险。改为两点，灰按钮竞态由循环重试覆盖。这也是上游 formal 模式禁用此路径（`_forbid_formal_pipeline`）的原因之一。

### 实测坑：入口确认后立即连点被页面吞掉

入口快查询确认 SKU 后 ~1ms 连点，3/4 失败（页面尚未接收触摸）；dump 路径天然时延 0.35-1.2s 从未失败。缓存路径补 0.4s 驻留后 3/3 直命中。

## 五、当前安全体系

- **提交改为审计制（E2E-14，用户决策）**：订单是否已取消/付款由用户人工确认，App 自身有「已有待支付订单」拦截，脚本侧记录闸门与之重复且状态跟不上现实——故 `submit_record.json` 仅留审计/取证（含待支付提醒 log），**不再拦截提交**；`--clear-record`/`--force-override-once` 降级为审计标记/兼容 no-op。
- **拦在提交前的核对（保留，这是真正的闸门）**：订单金额=expected_total、张数 ×1张、观演人在页且各出现一次、checkbox 实勾数≥观演人数。任一不过→停机交人工，不会点击提交。
- **决策点护栏**：CTA 文案护栏（dump 路径与 prewarm）；缓存路径无 dump，护栏由「入口轮询+订单核对+自愈链」兜底。
- **盲点边界**：缓存路径点击前零 dump——协议/验证弹窗出现时表现为「点击无效→超时→回退 dump 路径（有文案护栏）→STOP」，是「检测不到就停」，不是上游 PageProbe 的「识别分类处理」。真开票现场弹窗（待支付订单拦截/网络异常重试/人机验证）的自动识别**已规划、用户暂缓**（见「待办」）。

## 六、已知坑台账（本机 Xiaomi 14 / HyperOS / 大麦 9.0.38.6）

1. HyperOS 拒 u2 无障碍元素点击（`click()` 返回成功但 checked 不变）——元素点击后必须验状态，shell tap 兜底。
2. u2 `child(index=N)` 无 className+clickable 过滤时语义是「任意后代的首子」，坐标错位。
3. 入场动画期间 bounds 停屏外中间态（系统动画三 scale=0 根治，可逆）。
4. 入口确认后立即连点被吞（见上，0.4s 驻留解决）。
5. `strptime("%H:%M")` 默认 1900 年；anchor 采样必须紧邻且在 sample_clock 之后；sleep 粒度过冲累积（0.05s 粒度）。
6. 订单页有花呗分期金额（¥265.98 x 3期），金额正则必须精确匹配总额。

## 八、GPT 复验清单（更新版，--submit 实战前建议过一遍）

1. **缓存信任层**：`coords_cache.py` 廉价校验是否充分；缓存点错的自愈链（重测→再连点→元素回退→STOP）是否闭环。
2. **两点连点**：[票价,确定] 的灰按钮竞态覆盖；确认判定标记集（checkbox/确认购买/实名观演人/立即提交）是否有漏。
3. **checkbox XML 直读**：checked 属性语义在本机的可靠性（已实测 4 轮）；`attendees_checked` 核对逻辑。
4. **核对复用**：首帧字段已齐即复用 s2_after 快照——金额/张数在 ~0.5s 内变化的可能。
5. **wait-open T0 链路**：prewarm→T0 直点→入口→缓存坐标→连点，与 clock_sync 信任分级的交互。
6. **弹窗盲区**（已知未做）：缓存路径零 dump，弹窗场景=超时回退+STOP。
