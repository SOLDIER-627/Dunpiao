# 大麦真机端到端脚本：新演出预配置与开售运行

更新：2026-11-18。当前已有分步实测和[独立复验](../research/GPT独立复验_PH04_PH05_2026-11-18.md)，**尚无可无人介入运行的整套脚本**。本方案以 `reference/HaTickets` 的真机 u2/倒计时/状态机为主基线，结合本机大麦 9.0.38.6 的页面样本，实现“用户提前配置目标 → 脚本在详情页待命 → 开售后单次流程 → 到付款页停止”。预配置可人工完成；开售运行不依赖人工逐步点击。

## 先澄清页面动作

大麦底部文案可能是“立即预约”“立即预订”“立即购买”等，**不能把倒计时归零后固定点击‘立即预约’**。预约可能只是预约提醒，不一定进入购买。脚本以页面状态、按钮外观和点击后的实际跳转为判据：仅对经当前页面验证的购票入口点击；进入 SKU/场次页后才继续。文案和颜色只作辅助证据，不能单独证明有票。

本期的“选座”指**选场次、票档、数量、观演人**。如果页面进入真正的座位图、要求选择具体座位，归入独立适配分支；当前样本与脚本尚未验证座位图自动选座，遇到时停止并记录状态。

## A. 新演出前置准备（开售前完成）

1. **人工确认账户**：手机大麦 App 已登录；目标观演人已在官方 App 维护；实名信息与票数匹配。支付方式由用户本人检查，脚本不自动付款。
2. **建立演出档案**：记录项目 URL/标识、标题、城市、场馆、开售时间及 `Asia/Shanghai` 时区；列出允许的场次、票档、数量、最高可接受总价和候选优先级。把实值放入 Git 忽略的本地配置，仓库只保留无个人信息的模板。
3. **探测页面结构**：进入目标详情页，采集脱敏截图与 UI 树。若需先点场次才弹票档，按“详情 → 场次列表 → 选中场次 → 票档列表”的顺序建模。每个场次单独记录它对应的票档；切换场次后必须重新采样，不能沿用上一场的 `price_index`。
4. **遍历长列表**：在场次/票档各自的滚动容器内逐屏扫描，保存可见文本、bounds 和截图证据；去重后继续有限次数滚动，连续两屏无新条目或到达末端即停。目标未找到就报错，不默认选第一场/第一档。滚动会改变坐标，开售时必须重新定位。
5. **校准图片化信息**：当前版本部分价格不在无障碍树。先用截图/OCR 或用户人工标注建立“场次 + 票档名称/价格 ↔ 当前卡片”的对应关系；索引仅作同一场次、同一 UI 布局的临时线索。正式运行时订单页必须再次核对实际票档与金额。
6. **官方预选**：若该演出提供“设置本次抢票信息”，可由用户提前在大麦 App 选择场次、票档、数量与观演人；预选后重新进入详情页确认 App 是否保存。脚本不能假定所有演出都支持预选，也不能把预选状态当作真实库存。
7. **演练**：至少跑一次“到订单页即停”的完整自动流程，记录每个状态和耗时；再单独验证断线、错场、错价、票档售罄和未知页会停止。正式开售前再次打开目标详情页核对标题/场次与登录态。

## B. 开售时运行状态机

```text
设备与目标预检 → 详情页待命/对时 → 识别购票入口就绪 → 点击一次
→ 场次页（如有）匹配目标并选择 → 票档页匹配目标并选择
→ 数量/观演人确认 → 点击 SKU“确定” → 订单页逐项核对
→ 单次“立即提交” → 付款页/待支付状态确认 → 停止并通知用户付款
```

- **启动时机**：脚本在开售前已连接设备并停在目标详情页。使用 HaTickets 的时间等待机制，但以实际 CTA/状态变化触发动作；倒计时归零并不保证按钮已可购。对倒计时抖动和页面刷新设有限时、有限次数策略，未知状态立即停。
- **场次分支**：单场次可直接进入票档；多场次必须先准确匹配日期/时间/城市，再进入该场票档。场次可能要滚动；无法唯一定位时停止，不用 `fallback_index=0` 偷选。
- **票档分支**：按用户事先设定的优先级寻找可售票档。页面文字不可读时结合卡片结构、缺货标签、截图/OCR 与预校准档案；如果某档突然缺货，可按预设候选顺序换档，但不得超过总价上限或选择未授权场次。选择后核对“确定”按钮与新页面状态。
- **订单闸门**：读取演出、场次、票档、数量、观演人和最终金额。当前探针只读到数量、金额、观演人和提交按钮，**标题/场次/票档的订单页核对仍需补齐**。任一字段缺失/不符就停在订单页，不提交。
- **单次提交**：只有明确的正式运行模式才允许提交；点击前先持久化“本次目标已尝试提交”记录。点击后即使超时或页面未知，也不得盲重试同一提交。确认付款页或待支付订单后停止，支付由用户本人完成。
- **终点**：付款页面出现并不等于已付款或票已出票。运行结果只记为“待用户支付”；若出现排队、实名验证、座位图、登录失效或拒绝访问，则停机并记录待人工处理。

## C. 代码任务与验收

| ID | 实现 | 验收 |
|---|---|---|
| E2E-01 | 新演出档案与 `preflight` CLI：详情页、场次、票档逐屏采样；可恢复原页面 | 多场次先选场次再采票档；长列表可去重遍历；输出脱敏摘要与缺失项；不下单 |
| E2E-02 | 可复用的单进程运行器：设备预检、目标核对、开售等待、状态机与有界恢复 | 从详情页启动，自动到订单页即停；无需人在运行中点击；未知/断线/错场立即停 |
| E2E-03 | 场次与票档选择器：按当前页面重新定位，支持“场次 → 票档”依赖和有限滚动 | 不因 `session_index`/`price_index` 变化选错；候选唯一或证据充分才点；售罄与跨场次降级受配置限制 |
| E2E-04 | 订单摘要核验：标题、日期/场次、票档、张数、观演人、总价 | 全字段与配置一致才生成可提交证明；金额精确比较，缺失字段视为失败 |
| E2E-05 | 正式运行闸门与付款页终止：单次提交记录、幂等保护、结果日志 | 用户指定目标并开启正式模式后，从详情页无人介入到待支付页；最多一次提交；支付不自动化；异常后不重复下单 |
| E2E-06 | 回归与性能测量 | 用至少单场次、多场次、长列表、售罄/错价、断线样本复验；记录实测耗时，不能引用仓库标称速度当结果 |

推荐先交付 E2E-01～04 的**无提交完整演练**，确认能够独立抵达并正确识别订单页；E2E-05 在具体验收目标明确后再运行真实提交。现有 `scripts/ph05_flow.py` 是单场次 ¥780 的分步试验，金额硬编码、缺少完整新演出配置与开售等待，不能作为通用端到端入口。

## 当前实证与限制

- 已在同一演出上复现详情 → SKU → 订单页，且 SKU 是“选票档 → 点确定”两步；历史单次授权记录显示到达收银台，但日志分散，不能视作无人介入的单进程成功。
- 当前只有一个单场次/五票档样本；**多场次、场次滚动、票档滚动、真正座位图**尚未实测。上述任务是实现与验收要求，不是已具备能力。
- 上游 HaTickets 已有 `sell_start_time`、`select_session()` 与价格选择相关实现，可作为代码起点；本机 Android 16/大麦 9.0.38.6 的多场次和长列表行为必须重新验证。[HaTickets 购票逻辑](https://github.com/currycan/HaTickets/blob/master/docs/mobile-ticket-logic.md)也描述了场次选择分支。
