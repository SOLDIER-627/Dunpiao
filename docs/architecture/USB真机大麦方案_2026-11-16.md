# Mac USB 连接实体安卓手机：大麦方案与可识别性

> 历史可行性分析。当前实施以 [HaTickets 真机接入方案](HaTickets真机接入方案_2026-11-17.md) 为准；ADB 已保留，Appium/scrcpy 不作为首轮必需组件。

更新：2026-11-16。目标：电脑控制**用户自己的、近期已能登录大麦 App 的实体 Android 手机**，逐步实现可观察、可停止的单账号辅助流程。本文是技术可行性和验证计划；当时未连接该手机，也未安装 ADB/scrcpy 或运行订单自动化。

## 结论先行

**技术上可行，且不需要伪造真机。**手机仍运行原厂 Android、大麦 App 和原有账号会话；Mac 通过 USB 调试桥发送查看/控制指令。真机身份与操作方式是两个不同维度：实体手机可以被平台识别为真实设备，但调试/自动化行为仍可能被观察并触发不同风险判断。没有证据证明大麦“一接 USB 就拒绝”，也不能保证在真机上使用 Appium 就一定能下单。

## 对照：什么不变，什么会变

| 层面 | USB 接入后的状态 | 风险判断 |
|---|---|---|
| 手机硬件和系统 | 仍是原实体手机，不变成模拟器；不用改机型、root、解锁引导程序或替换系统 | 如果 App 检查真实设备/认证，真机具备模拟器通常没有的基础条件；并非通行保证 |
| 大麦账号 | 沿用手机中已经成功建立的登录态；不从电脑导出或注入令牌 | 减少重新登录这个已知失败关口；登录态仍可能过期 |
| 网络出口 | 大麦 App 默认仍使用手机自己的 Wi-Fi 或移动网络；USB ADB 本身不等于代理 | 服务端仍会评估 IP、账号和操作行为 |
| 调试与投屏 | 开启 USB 调试、授权这台 Mac；scrcpy 用 ADB 镜像和键鼠控制，不要求 root 或在手机持久安装 App | 调试环境与普通手点不同，风险不能说为零；目前无证据证明大麦直接以此拦截 |
| 自动化框架 | 后续如使用 Appium UiAutomator2，会在设备上运行辅助服务/测试 APK；直接 ADB 的只读截图不需要这一步 | 辅助组件可能成为额外环境信号，须单独验证，不能把“投屏成功”当作“自动下单成功” |
| 操作节奏 | 脚本可产生规律性和高频动作 | 大麦公开说明综合服务日志做风险判断；执行中要有明确停止、有限重试和单次订单闸门 |

大麦[官方隐私政策](https://help.damai.cn/helpPage.htm?pageId=109)说明 App 安全 SDK 可使用设备标识、IP、运行中应用和服务日志判断风险。Android [ADB 官方文档](https://developer.android.com/tools/adb)确认 USB 调试需开发者选项和手机端 RSA 授权。[scrcpy 官方说明](https://github.com/Genymobile/scrcpy)确认 macOS 支持 USB 镜像/控制，无需 root 或设备端持久安装 App。[Appium UiAutomator2 服务仓库](https://github.com/appium/appium-uiautomator2-server)说明其运行需在设备上部署测试服务。Google [Play Integrity 文档](https://developer.android.com/google/play/integrity/setup)展示一般的真实设备与虚拟设备完整性区分；**尚无证据表明大麦此次具体使用该 API**。

## 分阶段验证，逐步增加工具

| 阶段 | 实际动作 | 通过条件 | 失败时处理 |
|---|---|---|---|
| U0 现状 | 用户在不连接电脑时确认大麦 App 已登录，能浏览一场非热门演出 | 建立手动基线，不记录账号凭据 | 若已失败，先解决普通 App 问题 |
| U1 USB | 只装官方 Platform-Tools，手机开启 USB 调试并授权 Mac；`adb devices -l` 确认一台在线设备 | 手机原有登录态不丢失，普通浏览仍正常 | 检查数据线/授权；若大麦状态异常，停止工具升级 |
| U2 投屏 | 安装官方 scrcpy，用电脑人工浏览同一演出；手机可随时手动接管 | 画面/键盘/返回稳定，App 未出现拒绝页 | 关闭 scrcpy 后比对；记录何时变化，不反复登录 |
| U3 只读 | 用 ADB 或内置 UI 层级工具读取非敏感页面截图/控件树；运行本项目只读环境诊断 | 能识别演出详情、票档和异常页；不提交订单 | 若页面不可读，评估经脱敏的视觉识别；不安装多套框架乱试 |
| U4 自动化辅助 | 在 U1–U3 通过后，选择单一控制框架做低频、非热门场次的提交前流程 | 每一步读回页面；未知/断线/登录失效即停；展示完整摘要 | 如果装辅助组件后大麦异常，停止该框架并回到 U2 人工操作 |
| U5 订单验收 | 仅在用户决定实际验证时，单次人工监督尝试 | 最多一张有效订单，支付用户本人处理，结果可核验 | 出现拒绝/风控立即停，不做高频重试 |

## 最小环境

- Mac 上只安装 [Android 官方 Platform-Tools](https://developer.android.com/tools/releases/platform-tools) 与 [scrcpy 官方版本](https://github.com/Genymobile/scrcpy/blob/master/doc/macos.md)。不恢复本地 AVD、系统镜像或完整 Android Studio。
- 手机使用可信渠道的大麦 App，保持原有登录态。用户本人在手机上确认 USB 调试授权；使用可传数据的 USB 线。首次只运行 `adb devices -l` 和人工投屏。步骤见 [连接清单](../setup/真机连接验证清单.md)。
- `scripts/diagnose_android_login.py` 是只读环境摘要工具；连接后才运行，输出不含设备序列号、账号或令牌。截图与页面样本保存在忽略 Git 的 `pagesamples/`，分享前脱敏。

## 具体实施取舍

1. **先投屏，再自动化。**U2 可立即满足“在电脑上操作真机”的需求，也能单独检验 USB 调试与 scrcpy 对大麦现有登录态是否有影响。
2. **选一次框架。**页面层级充分可读时优先复用已有 UiAutomator2/Appium 参考；如果辅助服务导致异常，明确记录后退回人工投屏或仅用内置 ADB 只读操作，不在同一天反复切换框架。
3. **时间和状态比点击速度重要。**开售等待、超时、异常停止先落地；自动化任何动作都必须校验页面，不依赖无状态连点。
4. **不做设备身份伪装。**真机已经是真机；修改指纹、隐藏 root 或导入登录令牌不会提高这条方案的可验证性。
