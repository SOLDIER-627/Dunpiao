# dunpiao 整体计划

**日期：**2026-11-16　**目标：**分两步：**第一步**为大麦/猫眼演出与赛事的自有账号自购辅助（多账号并行 + Web 控制台）；**第二步**为多租户化，支持多用户各自使用自己的账号与设备。
**任务清单：**见 `TASKS.md`（本文只定架构与阶段）；技术选型依据见 `调研_多账号与Web控制台_2026-11-16.md`（含闲鱼代抢“换绑交付”模式观察）。

## 三、阶段划分

路线图分两步：**第一步 = 自有账号自购辅助（P0–P4）**，先把自己账号的抢票跑顺；**第二步 = 多租户（P5）**，在第一步架构上加租户隔离，不复制代抢的“换绑交付”模式（每个租户用自己的账号下单，订单天然归属租户，无需换绑，见调研文档第五节）。

### P0 单账号 MVP（当前，对应 TASKS DM-01~07）
目标：一台模拟器、一个账号，跑通"配置 → 等开售 → 选票档观演人 → 提交 → 停在支付页"。
- GPT：SDK/模拟器安装（已完成）、真机 ADB 接入与人工登录状态确认、页面样本采集、运行验证；模拟器登录当前受阻。
- Claude：`src/dunpiao/` 配置/日志/协调器/大麦适配器编码。
- 页面状态机：`未登录 / 演出详情 / 票档 / 确认 / 支付 / 售罄 / 弹窗 / 预约（预约/预售流程不支持下单）/ 未知`，未知即安全停止。
- **CLI 三模式**（吸收自 damaiTickets 实战设计）：
  - `probe`：安全探测，停在购票按钮前不点击，验证链路（定位、登录态、观演人已配）后手动停止；
  - `run --at "2026-04-06T12:00:00+08:00"`：精确开售时间，提前 `countdown_lead_ms`（默认 3s）进入高频轮询热路径；
  - `run --watch-cta`：不知道开售时间时守在详情页，等按钮从倒计时变为“立即购买”后进入热路径（超时默认 60s）。
- **热路径纪律**：城市/日期/场次预选在冷路径完成；开售瞬间只做“点 CTA → 选票档 → 勾观演人 → 提交”；单步等待 ≤2s、关闭系统动画与通知、优先坐标点击；失败重试 = 会话内回退详情页重进，**禁止重建 Appium session**。
- **提交闸门**：默认 `commit_order=false` 停在提交前；正式抢票需 `--yes` 显式确认（双重保险：CLI flag + 配置字段）。
- **配置字段沿用 damaiTickets 命名**：`item_url`（自动提取 itemId）、`users`（观演人姓名数组，人数即张数，上限 6）、`city/date/price` 按 App 原文匹配；**新版大麦把日期/票价画成图片读不到，必须有位置兑底**：`session_index` / `price_index`（第几个卡片，从 0 计，来自 ticket-purchase/damai-ticket-helper 实践）；本地真实配置走 `config.local.yaml`，不入仓库。
- **模拟器下单可行性是显式验收项**（真机不可用，见《调研_模拟器登录大麦风控》第七节）：按方案阶梯 S1–S3（指纹个性化、降级镜像、行为预热）逐项验证登录与下单；仍被拒则启用 S6 降级模式（自动化验证监控与页面状态机，下单人工完成），同时实测 S4（MuMu Pro Mac）。

### P1 设备池与多账号（对应 TASKS MA-01~05）
- AVD 模板克隆、设备注册表（serial ↔ 账号绑定）、并发内存预算。
- 每设备独立 worker；任务分发与错峰抖动（0–3s）。
- 同证件跨账号重复下单的前置校验（强实名约束）。

### P2 Web 控制台（对应 TASKS WEB-01~06）
- FastAPI + SQLite + WebSocket；React 前端。
- 批量配置（任务模板复制）、批次启动/停止、实时状态流、截图查看。
- CLI 保留：`python -m dunpiao run config.local.yaml` 与 Web 共用核心库。

### P3 猫眼适配（对应 TASKS MY-01~03）
- GPT 采集猫眼页面样本；Claude 增加 `platforms/maoyan.py`，复用协调器与设备池。

### P4 稳定性与风控对策（对应 TASKS ST-01~04）
- 页面改版回退（超时/售罄/登录失效/弹窗/支付页/重复订单六态）。
- 重试退避与抖动；运行报告（每任务结果、耗时、失败原因汇总）。
- **余票监控/捡漏模式**（吸收自 ticket-grabbing 思路）：独立于热路径的低频轮询，抢不到正场时监控回流票；发现票后走同一下单链路，通知用户人工确认。**回流票释放时间窗**（社区 7×24 轮询实测，见生态调研六点五节）：开票后 5–15 分钟（未支付过期）权重最高，演出前 3–7 天（退票）次之，每日 10:00–14:00 与演出前 24h 也有小高峰——监控调度按此加权。

### P5 多租户（第二步，对应 TASKS MT-01~05）
在 P2 的 server 架构上扩展：
- **租户模型**：租户 → 自己的账号/设备/任务，数据严格隔离；订单只落在租户自己的账号，不存在代抢方账号中转与换绑交付。
- **认证与权限**：本地多用户或局域网使用，租户只能看到自己的设备与任务。
- **配额与隔离**：设备池按租户分配并发额度；一租户的失败不影响其他租户。
- **前置评审**：若涉及为他人提供付费服务，需先完成平台条款与法律风险评估，产出使用条款；强实名场次下代抢与倒卖有法律风险，默认不提供。
- **交付方式结论**（详见《调研_换绑机制与交付方案对比》6.3/6.7）：按场次入场模式分层——刷证入场（模式 A）用观演人定向（M2）；三证合一场次（模式 B）票必须落在观演人自己的账号，由账号本人在设备上自助登录，不做持密码代登录；产品化主线始终是租户自购（M3）。
- **当前优先级**：先完成本机登录、自有账号的可行性验证（P0），单账号全自动流程跑通后再谈多账号与租户。

## 四、原则

1. **每一步先核对再操作**：页面状态与预期不符即停止，宁可少买不可错买。
2. **最多一次有效订单/账号/场次**：检测到已有订单立即终止该任务。
3. **不自动支付**：到支付页通知用户，人工确认。
4. **合规边界固定**（见调研文档第二节第 5 条）：不做滑块代解、签名逆向、代理池、批量注册；多账号仅限自有账号手动登录。
5. **单人单证约束**：系统按"账号 + 实名观演人"组织，同证件重复前置拦截。
