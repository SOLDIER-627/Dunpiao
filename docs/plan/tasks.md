## 决策与依赖

1. **设备载体：仅模拟器（真机不可用，2026-11-16 确认）**。采用“模拟器下单方案阶梯”（见《调研_模拟器登录大麦风控》第七节）：① AVD arm64 镜像（Apple Silicon 原生，无闪退实证）；② 指纹个性化（设备 profile + build.prop 机型伪装）；③ **行为预热**（提前数天同账号日常使用，避免“新设备立即下单”特征）；④ 节奏拟人 + 遇拒不硬冲；⑤ 部分场次用 Web 端（桌面 Chrome 真实指纹）替代。**不采用**：Magisk 隐藏、Xposed/Frida hook、签名逆向（超合规红线）。**预期管理**：模拟器下单可能持续被拒，P0 把“模拟器下单可行性”作为显式验证项；若验证失败，降级为“模拟器监控 + 人工半自动下单”，或改用 Web 端。
2. **多账号 = 多模拟器实例，一账号一设备**：不做同设备换登或双开（风控关联特征，见调研文档）。
3. **强实名约束**：多账号有效前提是每账号绑定不同实名观演人；同证件重复前置拦截。
4. **合规边界固定**：不做滑块代解、签名逆向、代理池、批量注册、自动支付；账号由用户手动登录。
5. **Web 是 CLI 的超集**：核心逻辑在 `src/dunpiao/`，CLI 与 Web 共用，先 P0 后长出 P1/P2。
6. **敏感信息不入仓库**：账号、验证码、证件号不进任何 git 仓库；`pagesamples/`、`config.local.*` 已 gitignore。
7. **两步走路线**：第一步自有账号自购辅助（P0–P4），第二步多租户（P5）；多租户订单只落在租户自己的账号，不复制代抢的“换绑交付”模式（见调研文档第五节）。
8. **不提供付费代抢**：若向多租户演进，需先完成条款与法律评估（MT-05）；强实名场次下为他人代抢并收费有法律风险。
9. **策略按入场模式分层**（见《调研_换绑机制与交付方案对比》6.7）：刷证入场（模式 A）用观演人定向，只需姓名+身份证号；三证合一场次（模式 B）票必须落在本人账号，由账号本人自助登录，不做持密码代登录。
10. **当前优先级：本机验证自有账号**。P0 单账号全自动流程跑通前，不做多账号与租户开发。
